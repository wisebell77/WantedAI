# `taxonomy/` — NCS 분류 체계

직무의 **주소**를 정하는 곳이다. 이름과 코드를 잇고, 문서 하나가 어느 분류에
속하는지 확정한다. 추천은 결국 "이 분류가 요구하는 역량"과 대조하는 일이므로
여기가 틀리면 그 뒤가 전부 틀린다.

## 파일

| 파일 | 내용 |
|---|---|
| `ncs.py` | `NcsTaxonomy` — 공식 분류표(대 24 / 중 83 / 소 279 / 세 1,114), `NcsNode`, `normalize` |
| `resolver.py` | `NcsResolver` — 문서 안 분류체계 표 → NCS 코드, `Resolution` |

공식표는 NCS-KECO 연계표(hwp)에서 뽑는다(`NcsTaxonomy.from_hwp`).
KECO 연계 343 직종도 같이 들고 있다 — 민간 직종명을 NCS 에 잇는 다리로 쓸 수 있다.

## 왜 문서에서 직접 읽는가

공고 API 가 주는 NCS 라벨은 **공고 단위**다. 공고 하나에 직무가 여럿이면
그 라벨이 모든 직무에 복사된다. 실제로 240건이 잘못 붙었다.
그래서 직무기술서 안의 분류체계 표를 읽어 **문서 자신의 분류**를 쓴다.

## 두 번의 실패

1. **칸 위치로 읽기** — 표의 n번째 칸을 소분류로 가정했더니 `01.해외관리` 자리에
   `양식조리`가 들어왔다. 공식표와 16% 가 어긋났다. → 위치가 아니라 **이름으로 조회**.
2. **너그러운 유사 일치** — "길이가 같고 한 글자만 다르면 같다"를 2글자 이름에
   적용하니 `기획`·`기술`·`관계`가 전부 `기계`와 매칭됐다. 기계가 24 → 80건으로 부풀고
   변호사와 연구원이 기계로 분류됐다. → **5글자 이상에만** 유사 일치를 허용.

## 해석 순서

```
세분류 이름 조회 → 소분류 → 중분류 → (실패 시) 대분류만
```

깊은 단계가 잡히면 코드에서 상위가 자동으로 따라온다.
대분류는 표의 코드+이름 쌍 → 칸 전체가 대분류 이름 → 헤더 다음 칸 →
헤더행이 끝난 뒤 첫 코드 칸, 4단계 규칙을 차례로 시도한다.
표준 코드가 없는 자체 개발 직무는 `is_self_developed()` 로 따로 표시한다.
`Resolution.how` 에 **어떤 규칙으로 찾았는지**가 남으므로 나중에 검증할 수 있다.

## 다른 폴더와의 관계

- `parse/units.py` 에서 분류체계 표 구간을 받는다.
- `parse/hwp.py` 로 공식표 hwp 를 읽는다.
- `recommend/matrix.py` 가 코드 → 이름 변환에 쓴다(화면에 코드가 아니라 이름을 띄운다).
- `recommend/scorer.py` 가 사용자가 입력한 직무 이름을 코드로 바꿀 때 쓴다.
- `collect/alio.py` 의 `NCS_MAJOR`(API 질의용 코드)와는 **다른 체계**다.
  저쪽은 `R600020` 같은 조회 코드, 이쪽은 `20` 으로 시작하는 표준 분류 코드다.
